## Goal

A personal assistant that works across the owner's Mac in the background while the owner keeps working: it does
tasks like a person would, perceives what happens on the Mac all day, and gets better at repeated tasks.
The language stays Python; a Rust rewrite was considered and rejected on 2026-10-06 (time goes to the model and to
apps/browsers, not to FERB's code; see Baseline).

## Requirements (owner's whiteboard, 2026-10-06)

- R1. Repeated tasks are learned: a counter per task type; past a threshold (count > 3) the task goes to `learned.db`.
- R2. Security, reliability, trust. No hardcode-heavy decision making.
- R3. Readable, concise trace logs.
- R4. A quick acknowledgment from FERB when the owner sends something.
- R5. Keep the abstraction between FERB's low level and the owner (the owner never deals with mechanics).
- R6. Continuous CLI chat: no loader blocks the prompt; the owner keeps typing while tasks run.
- R7. Clean, necessary, relevant task-completion answers.

## Shape (owner's whiteboard)

**Task loop:** task → semantic similarity search over past tasks → FERB (orchestrator), which receives identity
context and a concise capability directory (MCP-like), writes a task plan in a fixed schema, and decides whether to
answer directly or invoke workers. A direct answer must be verified, not just estimated.

**Always on (no task):** every event on the Mac is logged under a parent (app → window/tab), foreground and
background (a WA message, a Spotify song, a notification, a downloaded file, a created file, new software). Events
are summarized daily as history. Each task turn gets the last 10 minutes of events. Every ~10k tokens of events go to
Jev, which decides whether FERB should get this trail.

## Decided

- D1. Python stays; no Rust rewrite. Work happens on `astra/0.27-upgrade`, one topic at a time after planning.
- D2. Similarity search runs before FERB plans, giving it similar past tasks.
- D3. Chat is never blocked by a loader (R6).
- D4. Log every event on the Mac through system-wide sources, not per-app watchers: app/workspace events,
  an accessibility observer on every app, file system events, notifications, now playing (if feasible), and
  keyboard and mouse. Events are grouped by their app (bundle id), then window/tab.
- D5. No system log (`log stream`) monitoring: too much noise.
- D6. No continuous screen capture or text recognition. A screenshot goes with each task turn for visual perception.
  Clarified 2026-10-09 (owner: "at start of every task its sent, then on command of model"; not every model step,
  which would be too many screenshots): at the start of each task the model gets one screenshot of the window of the
  app the task works on, taken when the worker first starts on it (D26; D29: that window only, never the desktop);
  after that, screenshots go to the model only when the model asks (`mac.screenshot`, `browser.screenshot`); no
  per-step screenshots (per-step checks stay accessibility reads, D20). The model-bound screenshot is built in F5,
  right after screenshot redaction (D8, D13, D28), so no unredacted pixels reach a hosted model (rule 14).
- D7. Keystrokes are recorded **with content**, stored as text typed per field ("typed X into field F of app A"),
  not per key. This deliberately reverses the current rule in `ferb/sense/watchers/owner_input.py:1` and
  `ferb/sense/trail.py:10` (metadata only). Password fields are never captured (to verify by experiment, Q9).
- D8. Secrets are redacted **by code**, at capture, for a defined set of secret classes. They never reach a model,
  trace, log or the database. The owner can override for a specific item ("store this").
- D9. Raw events are kept N days; daily summaries are kept forever. Both are structured, idempotent, and retrievable
  by content as well as by date.
- D10. Jev gets a new job: filtering batches of events to decide whether FERB should see them. Batch size ~10k
  tokens, chosen because of Jev's context limit (OpenRouter docs: 32,000 tokens for state plus questions).
- D11. The clipboard is recorded, through the same code redaction.
- D12. Secrets are entered through a hidden secure input: FERB says it needs a secret, the owner types it into a
  hidden prompt, and the value goes straight to where it is used. No model ever sees it. Generalized (was P9): any
  secret type, browser and native apps, sealed fill straight into the field, optional "remember this" into the
  Keychain, split one-digit OTP boxes handled.
- D13. Screenshot redaction by code (was P7): on-device text recognition + accessibility password-field frames,
  secret areas blacked out before sending; the recognized text may go to the model too.
- D14. Retention: raw events 30 days; typed text and clipboard content 7 days; daily summaries forever.
- D16. One access level, no modes (owner, 2026-10-06; replaces P13): FERB gets full access, including Full Disk
  Access, and is made secure by design. The owner's underlying concern is destructive loss (e.g. erasing local

## Current orchestration (verified in code, 2026-10-06)

One request → the orchestrator returns one reply, clarification or **one task** (goal, identity, worker type,
targets, success conditions; `ferb/orchestrator/schemas.py:67`). One worker runs it; if it reports done, the
verifier checks the success conditions; anything unresolved becomes "blocked" and a dispatch model chooses retry
(possibly another worker type), ask, or finish (`ferb/orchestrator/supervisor.py:640-702`). Workers run one at a
time; there is no fan-out. Both runtimes are Codex in the owner's config. Prompt caching happens inside the
runtimes: 161M of 178M input tokens (90%) were cache hits across 719 usage records; small orchestrator turns show
no cache hits (inference: the owner's message is the first context block, so the prefix changes every turn).

- P17. Memory dashboard (owner, 2026-10-06): a clean local view of everything FERB remembers (identity, facts,
  procedures, lessons, episodes, summaries) with origin, evidence, confirm/edit/forget; served locally (localhost,
  token-protected) from the CLI first, later an option in the Mac app.
- P18. Keystroke capture rules from the field tests: primary defense is macOS Secure Input; secondary the focused
  field's role (works in Chromium, Safari, native; Firefox reports only the window); keystrokes are committed to
  the log only after ~0.5 s and dropped if Secure Input turns on for the same field in that time (catches the
  Chromium masked-field leak and the focus race); OTP digits are always visible, so code redacts digit codes typed
  into code/OTP fields and digits matching a code seen in a recent notification; CSS-masked fields in Safari and
  Firefox are fully visible (residual risk; idea to test: drop text when the field's accessibility value shows
  bullets instead of the typed characters).
- P19. Unknown outcome of a consequential action (payment, message to a person, deletion): never retried without
  the owner; FERB looks for other evidence (order page, bank/OTP notification) and otherwise reports exactly what
  is unknown and how the owner can check.
- P20. Prompt caching in all runtimes: stable content first (identity, rules, capability directory, tool list),
  changing content last (situation, recent activity, request); measure with `cached_input_tokens` in model.usage.
- P15. Large-input tasks (owner's example: pick the best of ~1.5 GB of local agent sessions, 576 files): code
  inventories the inputs; the orchestrator sets criteria (asks the owner what "best" means if unclear); workers
  each process one batch fully and write structured notes with evidence to files; a reducer ranks from the notes
  and re-reads the finalists; a builder makes the site; **code checks coverage** (every input has a note) before
  the task can finish. No worker holds everything; completeness is a code fact, judgment stays with agents.
  How the orchestrator decides the fan-out: code gives it facts (input count, sizes, token estimates, the worker
  model's context limit, concurrency limit from rate limits and the Mac); the plan schema gains map/reduce steps;
  code validates feasibility (each batch fits a worker's context; every input assigned) and sends a repair request
  if not (`repair.md` exists for plan validation); worked plans become procedures. Open: for big jobs, should FERB
  show the plan with a time/cost estimate before starting? (A cheap prefilter matters: ~1.5 GB of sessions is
  hundreds of millions of tokens before stripping tool outputs.)

## Verification audit (2026-10-06, code + read-only live DB)

How it works today:
1. The planner writes `success_conditions` (text, layer, optional code check: file_exists / file_contains /
   ledger_done / tab_url / account) in the chat turn (`ferb/orchestrator/schemas.py:35-49`); retries never rewrite
   them.
2. The worker reports done / failed / needs_user / blocked with summary, artifacts and evidence.
3. Only on "done": code pre-checks (files, the task's tab URLs; `ledger_done` always returns "unknown",
   `ferb/orchestrator/verify.py:73-77`) are passed as observations to a separate checker model (`verifier.md`),
   which may read the recorded tool results (`task.evidence`, no images) and do fresh reads. It returns
   met = true / false / unknown per condition.
4. Anything not "true" → "blocked" → the dispatch model picks retry / ask / finish (no retry cap).
5. Final: done only if every condition is true; otherwise failed (or needs_user) with one line per condition,
   "— failed" or "— unverified" (`ferb/orchestrator/supervisor.py:885-893`).

The action ledger (`ferb/policy`, gateway) records non-reversible tool calls (mac.act/click/menu, AppleScript —
even read-only scripts — browser clicks/typing, shell, file writes). "done" there means the input was delivered,
not that the goal happened. mac.open, browser.open and snapshots record nothing.

Still broken in current code:
- When no check ran, the owner still sees "unverified" lines, and the worker's real reason is hidden unless the
  dispatch model fills `stop_reason` (all 4 non-done outcomes since 0.26).
- Screenshots are never stored as evidence, and brief states (a toast, a ringing call) are gone by the time the
  checker looks (~5 of 23).
- No per-step verification: tools return "delivered, take a new snapshot"; re-reading is left to the worker.
- "Unverified" and "failed" share the status `failed`; `ferb stats` can't tell "didn't do it" from "couldn't check".
- The checker has the worker's full action permissions; "inspect only" is prompt-enforced.
- `ledger_done` is legacy noise; read-only AppleScripts create ledger rows.

- P16. Verification design (draft):
  - V1. Evidence is observed state captured at the moment and stored (redacted screenshots and snapshots, 30 days),
    so the checker can re-inspect brief states.
  - V2. After each action, tools return what changed (a short after-state read), not just "delivered"; procedure
    "expect" lines are compared with it. A mismatch is a fact for the worker.
  - V3. The final checker is read-only, enforced by code.
  - V4. Three outcomes: done (verified) / done but unverified (with what is unconfirmed and how the owner could
    check) / failed, each its own status.
  - V5. The owner always sees the real reason; "unverified" only when a check ran and couldn't confirm.
  - V6. Conditions describe the outcome the owner wants and how it can be observed from the background; drop
    `ledger_done`.
  - V7. The ledger is for recovery (what may have happened before a crash), not proof of success; read-only
    scripts stop creating rows.
  - V8. Memory counts a success only with V1 evidence; procedures store how success was verified.
- VQ1–VQ4 decided (D20). VQ5 → P19.

- 2026-10-07, prompt caching (live, FERB's pinned Codex, gpt-5.5, separate `codex exec --ephemeral` processes,
  ~17.8k-token prompt): same start of prompt → 1,536 then **16,896** cached tokens (95%) on the second call;
  first line changed each time → 0 and 1,536 cached. Separate sessions do not prevent caching; the order of the

## Security proposal (draft, 2026-10-06; all Proposed)

Grounded in two research passes: security-by-design for agents, and a catalog of 38 real documented attacks
turned into FERB test cases (`docs/0.27_SECURITY_TESTS.md`).

Facts that shape it:
- Model-level and detector defenses all broke under adaptive attack (12 defenses, 71–100% automated attack
  success; https://arxiv.org/abs/2510.09023). Only system-level controls give guarantees.
- FERB has a good enforcement point: the runtimes' built-in tools are off (Claude `tools=[]`,
  `ferb/runtimes/claude_sdk.py:49`; Codex read-only sandbox, web search disabled, `ferb/runtimes/codex_exec.py:117`),
  so every action and result passes through FERB's daemon, whichever model runs.
- The biggest hole is the shell: a plain `Popen` (`ferb/act/shell/pty_proc.py:42`); network use is annotated,
  not controlled (`ferb/act/shell/guard.py:1-3`). With Full Disk Access, a shell command can read anything and
  send it out.
- No backups exist (Time Machine has no destination). `fs.trash` exists (`ferb/act/fs/files.py:217`).

Layers (code enforces facts and boundaries; agents decide; the owner confirms only narrow cases):
- S1 Recovery: Time Machine (owner); APFS clone copies of files before FERB modifies or deletes them (kept 7
  days); a local APFS snapshot before bulk or destructive work (whether it needs admin rights: to verify);
  deletion through tools goes to the Trash with the original path recorded.
- S2 Containment (still one mode): the shell runs under a macOS sandbox profile: reads allowed, writes denied
  to protected paths (FERB's own stores, browser profiles, `~/.ssh`, `~/Library/Keychains`, system folders),
  network only through a FERB proxy that records destination and size.
- S3 Provenance: every tool result is labeled by origin (owner / private local data / external:<source> /
  FERB's own); a task that has read external content is marked; each consequential argument (recipient, URL,
  amount, path) is matched against the owner's words, contacts and known destinations.
- S4 Sink rule, the only confirmations: (a) private data going to a new destination after external content was
  read; (b) a destination or amount that came only from external content; (c) irreversible bulk work, shown
  concretely (count, size, sample); plus P19 (never retry a consequential action with an unknown outcome).
  Everything else runs and is logged. Confirmations carry across retries.
- S5 Reading untrusted content in bulk (mail, groups, web) through workers or the typed model (Jev) with
  constrained outputs, so raw untrusted text rarely reaches the orchestrator (dual-LLM / map-reduce patterns).
- S6 Alignment check: the typed model sees the owner's request and the proposed action's metadata (not the raw
  content) and flags mismatches to the orchestrator; logged; one layer, never the guarantee.
- S7 Memory: origin-bound authority (MP2); procedures learned from tasks that read external content stay
  quarantined until the owner confirms (digest); deletion cascades; dashboard (P17).
- S8 Secrets and identity: sealed fills and Keychain access through a small signed helper; stable app identity
  for macOS permissions (FERB.app launcher); Developer ID later (owner).
- S9 Evaluation: the 38-scenario suite on owner-controlled surfaces (FERB's Gmail/Discord, test pages on an
  owner-controlled domain with a request-logging server, the owner's second WhatsApp account, local files), canary
  strings in private data, pass/fail from traces (canary reaching an outbound action, attacker-chosen recipient,
  memory gaining authority, deletion outside the Trash), at least 5 runs per case, a benign twin per case to catch
  over-blocking, rerun on every prompt or model change.
- S10 Visibility: a daily digest of new destinations, confirmations, blocked flows and memory items of external

## Memory design proposal (draft, 2026-10-06; all Proposed)

Grounded in three web research passes (cognitive architectures, procedural memory for computer-use agents,
storage engineering incl. measurements on this Mac). Key sources are listed at the end of this section.

Principles:
- MP1. Raw evidence is append-only, redacted at capture, and the source of truth. Everything derived is tagged
  with how it was made (extractor, model, prompt version) and can be rebuilt; IDs are deterministic.
- MP2. Trust follows origin, permanently: owner-typed, owner-confirmed, FERB's own action, external content,
  FERB-inferred. Derived items inherit the least trusted source. Only owner-origin items carry preferences or
  authority. Defends against memory poisoning (a WA message can't become a rule).
- MP3. Facts are invalidated, never overwritten (valid time + recorded time). Owner deletion is the exception and
  cascades through everything derived from the deleted source (summaries, indexes, embeddings).
- MP4. Agents working on tasks don't rewrite memory; an offline "sleep" consolidator does, as small incremental
  changes, each logged so it can be audited and rolled back.
- MP5. Learn only from verified outcomes. Lessons from failures are scoped (app/site/intent) and tied to evidence.
- MP6. Code finds candidates (keyword + meaning + time + app/person filters); agents decide relevance and whether a
  past task is "the same type".
- MP7. Memory must prove it helps: a FERB evaluation set from the owner's own history, comparing with and
  without memory (published results: memory sometimes hurt strong models).

Stores:
- L0 Evidence: activity events (weekly shard files; typed/clipboard text in daily shards; deleted by file at
  retention), task traces, chat.
- L1 Episodes: one record per task (request, intent signature, slot values, apps + versions, surfaces used,
  outcome verified/unverified/failed/stopped/blocked, verification evidence, owner feedback, reflection, short
  narrative); one per day (today's daily summary, now citing its sources); week/month/year rollups that cite
  their children; small evidence cards that outlive purged raw rows.
- L2 Semantic: facts and entities (people, accounts, places, projects) with validity times, origin, evidence and
  confidence; entity summaries.
- L3 Procedural: procedures (intent, typed slots, preconditions incl. app version, abstract steps, how success
  was verified, UI hints, counters, status candidate → learned → suspect → retired) and lessons (scope, trigger,
  text, contrasting episodes, helpful/harmful counts). Shown like skills: name + one line always, body on demand.
- L4 Identity: small, always-loaded, version-controlled text: FERB's role, invariants, the owner's durable rules.
  Only owner-origin content; the consolidator may only propose changes.

Lifecycle:
- Online (code): events → L0; task end → task episode from the trace, the orchestrator's outcome and the check.
- Sleep (idle/nightly): replay the day weighted by salience (failures, owner corrections, novelty, explicit
  "remember"); write the day episode; facts add/update/invalidate/no-op; induce or update procedures from verified
  task episodes; lessons from failure→success contrasts; rollups; log every change.
- Learned (R1): at least 3 verified successes, across at least 2 different slot values, latest on the current app
  version. A fact agents read, not a gate. Learned procedures may take a fast path with a check after every step
  and a final verification; any mismatch falls back to full reasoning. Suspect after consecutive failures or an
  app version change.
- Before planning (D2): code retrieves candidate task episodes, procedures, lessons and facts; the orchestrator sees
  one-line entries and decides; workers get the chosen procedure's details.
- Forgetting: decay only lowers ranking; deletion only by owner request or retention.
