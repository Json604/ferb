# FERB Notch

Native macOS 14+ front end for the local FERB daemon. The notch geometry, pinning, shortcuts, Spaces behavior, sounds and reduced-motion handling are preserved from the existing design.

## Run

Install/update the backend from `~/Desktop/FERB` with `ferb setup --update`. Build this app with `./build.sh`, then open `build/FERB Notch.app` (it keeps the development identity `dev.ferb.notch`). The app connects to `~/.ferb/run/ferb.sock`; this development build never starts, installs or restarts the daemon. The packaged FERB.app (`scripts/build-app.sh`, L27) is the same app with FERB's Python inside: at launch it runs its own `ferb setup` in a console window when nothing is installed, `ferb setup --update` in the same window after the app was replaced by a new build, and asks before replacing an installation that runs from elsewhere (`AppSetupPlan`, decided from `~/Library/LaunchAgents/com.ferb.daemon.plist` and whether launchd has FERB running; a stopped service is repaired with `--update`). The menu bar's Set Up FERB… goes through the same decision (asking before a replacement) and runs the full setup otherwise. Closing the console doesn't stop setup; quitting the app stops it after setup finishes reinstalling the service. The daemon itself runs as `Contents/Helpers/FERB.app` (`ui/mac/FERBAgent`), a native stub embedding the app's Python, so macOS names FERB in permission prompts. Profile → Reconnect to FERB reconnects without resubmitting a request. Closing the notch or quitting the app leaves daemon tasks running. Stop targets the selected backend task, including when Stop was pressed before planning finished.

The socket authenticates as the owner CLI. `chat.attach` resumes the conversation. `chat.send` streams actual task progress and results. `logs.subscribe` observes background changes (a `bus.dropped` or `bus.overflow` notice triggers a fresh status read), and `chat.status`/`trace.get` reconcile running tasks, pending prompts and completed results after disconnect. `chat.status` is polled with `peek:true`; every result it returns is placed in the chat, including tasks started elsewhere (CLI, voice, schedules), filed on the day the result arrived, and each placed result is then acknowledged with `results.ack {task_ids}`, so `ferb chat` replays only what this chat didn't show. While today's chat is open, the day's learning digest (`memory.learning {op:"digest"}`, which marks it seen) is shown with Confirm (`op:"confirm"`) and Not right (`op:"retire"`) per item. An archive the app can't decode is kept aside under a `FERBConversationArchive.unreadable-…` key, never saved over, and a new archive starts. The UI persists its conversation turns (the owner's sent messages included), timestamps, task IDs, FERB's lines, answers, notices and artifact paths locally in preferences. The unsent composer draft is kept in memory only and never written to preferences (L20); secret answers never enter the conversation. A task this chat didn't send (reconnected after a restart, recovered, or started elsewhere) shows the daemon's goal as FERB's description on FERB's side, never as an owner bubble. Today is one continuous chat; the visible History control opens date tabs for earlier days. The daemon conversation ID stays the same across days. Existing CLI-only transcripts are not imported by the current daemon RPC. The backend retains its normal task records.

Attachments are sent as explicit file paths only when the daemon advertises `input_paths`; older daemons show an update requirement instead of dropping the files. Pasted reference text retains data provenance without any dialog: the composer reports each edit exactly, so pasted characters (Command-V, dropped or Services text, and text put back by undo/redo) are sent inside the CLI's bracketed-paste delimiters as data, and the words the owner types, before, after or inside a paste, stay theirs. A whole paste with nothing typed is sent as data. If a change the composer didn't report reaches a paste, the whole draft is sent as data rather than guessing. Control escape characters in reference text are represented visibly as `\u001b` to prevent forged frame delimiters.

Questions appear inline at the end of today's chat and the composer stays usable while one is open: a typed message can answer it or start other work. A question never takes keyboard focus by arriving or by the panel refreshing (typing that grows the composer only updates geometry); its field is focused only when the owner clicks the question or chooses Answer request in Tasks; the question is then scrolled into view and its field keeps focus over the composer until it loses focus, the question is resolved or the notch hides. Password, OTP and secret requests use a separate secure field in the question, which always names its task (the goal, or "Task" and a short id). Hidden values never enter the normal composer, UI history or activity. The field clears before sending, when changing prompts and when hiding the surface. Requests are not automatically retried after an uncertain connection failure. Free-text and hidden answers use `chat.answer`. Option buttons send their exact one-based ordinal through `chat.approve`; Cancel/Decline uses `chat.approve` with `granted: false`.

Results show the actual daemon answer and reported status; an unverified or failed result is not labelled Done. Only explicit absolute artifact paths become Open, Quick Look, Reveal and drag actions. No example PDF is generated by task submission or file actions.

Dictation now uses AVAudioEngine and Apple Speech in the notch app. Click the microphone or hold right Command + Option; release or Stop ends capture and places the real transcript in the composer for review. Microphone and Speech Recognition permission are requested on first use. Recognition runs on this Mac only: where on-device recognition isn't available for your language, dictation says so and doesn't listen, so your voice never goes to Apple's servers. No audio files are saved. Cancel, hide, or switch to typing stops capture. Releasing during a permission prompt prevents capture from starting later. Secret approval fields remain separate from dictation and chat history.

Live daemon task events update the working row and activity view immediately. When the installed daemon emits `reply_delta {text}`, the frontend renders those real chunks in the matching turn, labelled “Draft · still responding.” Drafts do not trigger completion sounds, notifications or status. Authoritative `reply`/`clarify` text replaces the draft, while `plan` clears it and switches to task progress. `reply_abort {reason}` or a connection interruption clears the incomplete draft and records an interruption instead of a completed answer. This requires a daemon/runtime that emits real deltas; older daemons still show complete replies without fake typewriter delays. Both final direct replies and task outcomes automatically reveal the notch without requesting keyboard focus. Startup restoration is silent; newly completed tasks recovered during a disconnect still reveal it.

Each turn shows the daemon's `ack` at once as a FERB line, then the `plan` text as the next FERB line (no longer filed in the activity view). While the task works, one live line under the plan shows the latest `progress` step and the time since its `started_at`; each step replaces it, and it disappears when the answer arrives or the stream ends. An answer whose turn is no longer the last entry in the chat appears at the bottom as a reply with a one-line quote of the question, and the original turn reads “Answered below”; History keeps both. Events are tied to their turn by `request_id`; an event naming another turn's request is not applied. A `verified` outcome shows a small check mark. The live line is not saved; the acknowledgement, plan line, request ID and late-reply placement are. When a task that asked a question (`needs_user`) later finishes, the question stays where it was shown and the final answer is placed like any late answer. Perception notices (`attention.notice`, and unacknowledged `chat.status.notices`) appear as FERB messages with a small "noticed" tag, with any outside text they quote shown as a plain-text quote with its origin; they are saved, then acknowledged with `attention.ack {ids}`, and they don't open the notch, take focus or play a sound.

Microphone route changes use the current hardware input format. A small Objective-C boundary converts AVFAudio exceptions into recoverable errors before they can unwind through Swift tasks; cleanup is protected too. The format-change and exception paths have regression tests; live dictation while switching audio devices still needs owner acceptance.

When the daemon finds a missing startup profile, the inline question shows the proposed app-use profile and an expandable evidence list. Save, edit or skip uses the same approval contract as the CLI; no preference is confirmed automatically.

FERB yields to other apps. Its windows live in an unmanaged overlay space above every ordinary window and other apps' menus, so instead of competing on window level the panel is ordered out while any reason holds and ordered back into the overlay space afterwards, exactly as it was (draft, attachments, pin and fold unchanged; it takes keyboard focus back only if it had it and the owner didn't click or switch to another app meanwhile). Mouse-event transparency is never toggled: once `ignoresMouseEvents` has been set on a window, AppKit stops passing clicks through its transparent margins. The reasons: FERB's own file picker is open; another process's menu, popover or floating window (window layer above normal, alpha at least 0.05) overlaps FERB's drawn surface, checked from the window list (number, bounds, layer, owner and alpha only, never window titles, so no Screen Recording permission) five times a second only while some part of FERB is on screen, which means continuously while FERB is pinned and the displays are awake; or, for a pinned chat, the owner brought forward or clicked into an app with a window under the chat's drawn surface. The menu bar strip, status items, the Dock layer, nearly invisible windows, whole-display overlays and system text-input windows (accent popup, emoji and symbols palette, input-method candidates, input-source switcher, identified by bundle identifier) never count, and the folded pinned header sits in the menu bar, so it doesn't yield to ordinary windows. When the owner opens or reveals FERB (shortcut, menu, click, hover), enters or clicks the notch, or dictates, FERB stays over the other apps' windows then over it (a screen-share bar, another notch app) until they leave the screen; a window that newly overlaps FERB hides it again, and a menu over the notch is never overridden by hovering it. Bringing FERB back by hovering or clicking the notch focuses the visible text input, like the shortcut. FERB coming forward, another app without a window under the chat coming forward, or that app's windows leaving the chat also return it. Dictation is never hidden. A question that arrives while FERB yields still plays its sound and keeps the amber camera-edge light (that window only draws the glow and never takes a click); the question is already open in the chat when FERB comes back. The volume and brightness HUD briefly makes FERB step aside when it overlaps it.

## Checks and shipping

Run `swift test` and `./build.sh`. Tests cover a temporary Unix socket server, fragmented RPC framing, auth, stream filtering, approval routing, task recovery, stop-before-plan, provenance, results and existing notch layout/shortcut behavior. They do not call a model or operate the installed daemon.

The development build is locally ad-hoc signed. The packaged FERB.app is signed once by `scripts/signing.sh` with the hardened runtime: ad-hoc now; a Developer ID identity re-signs the same bundle and notarizes it (`scripts/build-app.sh --sign-only`). It still needs owner live acceptance. The unmanaged SkyLight overlay remains a private API dependency with the existing AppKit fallback; do not describe this build as App Store ready.

The conversation uses compact Messages-style bubbles and a 240-point minimum reading area when messages exist, growing to 320 points before scrolling; the empty dialog remains compact. The native composer consumes Return, accepts Shift–Return for a newline, and keeps IME composition intact. Submission is silent. You can send further messages during work: each local stream tracks its own task, while the daemon orders routing until work is registered (`supervisor.send`) and runs tasks independently. Submitting clears the composer immediately; incoming replies never erase an in-progress draft.

### Task controls and quiet updates (2026-10-11)

Open **Tasks** from chat to see individual active and completed tasks. **Inspect** shows that task's progress, result, artifacts, and an optional full task record. **Stop task** sends only that task's ID; a request still awaiting its ID remembers its own stop request. There is no ambiguous aggregate Stop button.

Background replies and progress update the transcript/status and completion glow without opening the notch or cancelling dismissal. This follows the owner's latest request and supersedes the earlier automatic answer expansion. Cmd-V uses the native Edit menu and composer shortcut; pasted text retains its provenance.

Daemon `display_text` is shown when supplied, with **Details** retaining the complete reply or ordinary question. Older daemon events and saved history without the field keep their original text. Secret values remain only in the secure answer field.

### Large task records

Inspect keeps the task summary and activity in the notch. **Open full task record** opens the complete JSON export; **Reveal** locates it in Finder. Serialization runs off the UI thread, and private temporary files retain the whole record without a size cap. Switching or hiding an inspection rejects late responses. Socket framing scans each incoming byte once rather than rescanning the accumulated response.

Freeze repair validated 2026-10-13: 99 native tests and release build passed. The owner’s 35.6 MB trace loaded through the patched Swift transport in about 0.5 seconds. Previous samples showed main-thread CoreText layout at 100% CPU, then repeated socket-buffer scanning after UI restart. Only the UI was relaunched; the daemon was not restarted.
